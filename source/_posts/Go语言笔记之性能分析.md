垃圾回收算法
--------------------

Go语言中的垃圾回收（GC）算法是其自动内存管理的核心机制，采用**并发标记-清扫（Concurrent Mark-Sweep）**技术，结合**三色标记法**和**增量回收**策略，旨在减少程序停顿时间并提高性能。

三色标记法将程序中的对象分成白色 黑色 和灰色三类：

- 白色：未被访问的对象, 潜在的垃圾，可能会被回收
- 灰色：已被标记但子对象未完全扫描的对象
- 黑色：活跃的对象，不会被回收

### GC工作流程

1. **标记准备（Mark Setup）**: **STW暂停**，完成准备工作如开启写屏障。记录根对象（全局变量、栈变量、寄存器等）。
2. **并发标记（Concurrent Marking）**: 后台线程扫描根对象及其可达子对象，标记为灰色，逐步推进至黑色。 用户程序继续运行，写屏障拦截指针修改，确保标记正确性。
3. **标记终止（Mark Termination）**: **短暂STW暂停**：完成剩余标记，确保所有存活对象标记为黑色。统计存活对象，准备清除阶段。
4. **并发清除（Concurrent Sweeping）**: 回收未被标记的白色对象内存，交还给堆管理器。用户程序无感知，持续执行。


### 写屏障

垃圾标记和正常程序是同时进行，所以有可能出现标记错的情况，比如扫描了a 以及a所有的子节点后，这时候用户建立了a指向b的引用，这时b是白色会被回收，所以引入了屏障。它可以在执行内存相关操作时遵循特定的约束，在内存屏障执行前的操作一定会先于内存屏障后执行的操作。屏障有两种，写屏障和读屏障，因为读屏障需要在读操作中加入代码，对性能影响大，所以一般都是写屏障。

业界有两种写屏障 ： 插入写屏障和删除写屏障 1.7用的插入写屏障 1.8用的混合写屏障

- 插入写屏障： 当A对象从A指向B改成从A指向C时，把BC都改成灰色。
- 删除写屏障：在老对象的引用被删除时，将白色的老对象改成灰色
- 混合写屏障 ：将被覆盖的对象标记成灰色 & 没有被扫描的新对象也被标记成灰色 & 将创建的新对象都标记成黑色

> 屏障必须遵守三色不变性 ： 强三色不变性:黑色对象不会指向白对象，只会指向灰色对象或者黑色对象 弱三色不变性：黑色对象指向的白色对象必须包含一条从灰色对象经由的多个白色对象的可达路径

### 垃圾回收触发条件

1. **堆内存阈值**：默认当堆内存增长到上一次GC后的2倍（由`GOGC`环境变量控制，默认值100%）。
2. **定时触发**：防止长时间未触发GC导致内存激增（2分钟强制触发一次）。
3. **手动触发**：通过`runtime.GC()`函数主动触发（通常不推荐）。

### GO与Java垃圾回收的区别

GO语言与Java语言的垃圾回收机制均旨在实现自动内存管理，但在设计哲学、实现细节及适用场景上存在显著差异。以下从算法、并发性、内存模型、性能表现等方面详细对比二者的异同点：

1. **算法与分代设计**

| **特性**               | **GO语言**                          | **Java语言**                          |
|-------------------------|-------------------------------------|---------------------------------------|
| **基础算法**           | 并发三色标记-清除（无分代）         | 分代收集（新生代+老年代）+多种算法选择 |
| **分代假设**           | 不依赖分代假设                     | 强分代假设（对象大多朝生夕死）       |
| **回收策略**           | 全局混合回收                       | 分代回收（Minor GC + Full GC）        |
| **典型GC算法**         | Go 1.5+的并发标记-清除             | G1、ZGC、Shenandoah、CMS、Parallel GC |

**关键点**：  
• **Go无分代**：假设对象生命周期无明显规律，采用统一内存空间，简化实现但可能增加回收成本。  
• **Java分代**：通过Young/Old区划分，优先回收新生代（复制算法），提升短期对象回收效率。

2. **并发与停顿时间**

| **特性**               | **GO语言**                          | **Java语言**                          |
|-------------------------|-------------------------------------|---------------------------------------|
| **STW阶段**           | 仅初始标记和终止阶段短暂STW（微秒级）| 某些算法（如G1）在标记开始/结束需STW  |
| **并发能力**           | 全并发标记与清扫                   | ZGC/Shenandoah支持全并发，CMS部分并发 |
| **最大停顿目标**       | 通常<1ms（Go 1.14+）               | ZGC/Shenandoah可控制在10ms以内       |

**关键点**：  
• Go的GC设计更强调低延迟，适合实时性要求高的场景（如游戏服务器）。  
• Java通过ZGC等算法在超大堆（TB级）下仍保持低停顿，适合企业级应用。

3. **内存模型与分配策略**

| **特性**               | **GO语言**                          | **Java语言**                          |
|-------------------------|-------------------------------------|---------------------------------------|
| **对象分配**           | 基于协程栈的逃逸分析，优先栈分配    | 对象几乎全堆分配                      |
| **内存布局**           | 连续内存块（mspan管理）             | 分代内存区（Eden/Survivor/Old）       |
| **内存压缩**           | 无内存碎片整理                      | G1/ZGC支持部分整理，避免碎片          |

**关键点**：  
• Go通过**逃逸分析**将未逃逸对象分配在栈上，减少GC压力。  
• Java因分代需处理跨代引用（Card Table、Remembered Set），增加开销。



函数内联
---------

GO几乎不做复杂的优化, 但如果一个函数被内联到另一个函数内部, 那么只需要进行一些常规的局部优化, 往往就可以达到比较好的效果. 因为内联消除了函数调用时的入参拷贝和返回值拷贝, 函数内部的表达式还可以与外部的变量一起参与常量折叠, 死代码消除, 公共表达式提取等常规优化. 所以GO非常重视函数内联, 可以说是性能优化中相当重要的一环.

---

### 🎯 两阶段流程：先筛选，后决策

Go 编译器的内联过程分为两个明确的阶段：

1.  **`CanInline`（资格筛选）** ：编译器首先遍历所有函数，判断每个函数**自身**是否“有资格”被内联。一个函数如果通过了资格检查（比如没有硬性限制，且函数体足够“便宜”），它的函数体副本会被保存下来，供后续使用。
2.  **`InlineCalls`（调用点决策）** ：然后，编译器会遍历所有函数中的每一个**调用点**，结合调用者自身的状况（如是否是大函数）和被调用者的成本，做出最终是否展开内联的决定。

这意味着，一个函数能否被内联，既取决于它**自身**的属性，也取决于**具体的调用上下文**。

---

### ⚖️ 核心引擎：基于“毛发”的成本模型

内联决策的核心是**预算与成本的比较**。Go 编译器使用一种抽象的“毛发单位”来衡量函数的复杂度。

**默认预算**是 `inlineMaxBudget = 80` 个节点。编译器会遍历函数体的抽象语法树（AST），为不同元素累加成本。如果总成本超过 80，函数通常就失去了内联资格。

一些关键的成本参数塑造了模型的偏好：

- **`inlineExtraCallCost = 57`**：一次**普通的函数调用**会消耗高达 57 的预算。这个高惩罚直接解释了为什么**非叶子函数（包含普通调用的函数）默认极难被内联**——一次调用就几乎耗尽了全部预算。
- **`inlineParamCallCost = 17`**：通过**函数参数**进行的调用，成本大幅降低至 17。这是编译器一种精明的“投资”：它愿意用较低的门槛鼓励内联这类函数，因为内联后，作为参数传入的具体函数可能会“现出原形”，从而解锁**常量传播、死代码消除**等后续高价值优化。例如，内联 `apply(f, x)` 后，`f` 如果是一个简单函数，就可能被二次内联，让 `apply(double, 5)` 在编译期直接算出 `10`。
- **`inlineExtraPanicCost = 1`**：`panic` 的成本被设得极低，基本是鼓励内联的。
- **大函数限制**：如果**调用者**本身是一个非常大的函数（节点数超过 5000），它能内联的**被调用者**的最大成本会被限制在 `inlineBigFunctionMaxCost = 20`，以防止大函数因内联而进一步膨胀。

---

### 🍃 叶子函数的清晰标尺

对于**叶子函数**（不包含任何普通函数调用），由于没有 57 点的调用成本，判定标准变得非常清晰：**几乎完全取决于函数体本身的 AST 节点数量**。

一个最直观的经验法则是：**如果一个叶子函数在 AST 层面的节点总数超过 80，它基本上就不会被内联。** 一个简单的算术表达式（如 `return a[0] + a[1] + a[2]`）成本很低，而包含大量局部变量、复杂控制流（如大 `switch`、`select`）的函数，其节点数会迅速逼近阈值。

```go
// 叶子函数：无调用，成本仅来自自身节点，很容易内联
func leafAdd(a, b int) int {
    return a + b // 成本极低，会被内联
}

// 叶子函数：较复杂，节点数可能超标，有内联风险
func leafComplex(a []int) int {
    sum := 0
    for _, v := range a { // 循环、range 都会增加成本
        sum += v
    }
    return sum
}
```

---

### 🚫 硬性限制：直接否决的情况

除了成本超标，某些情况会**直接导致函数无法内联**，无论其成本多低：

- **没有函数体**（如汇编函数）。
- **递归函数**，直接递归会导致无限展开。
- **调用了 `runtime.getcallerpc` 或 `runtime.getcallersp`**，这些函数依赖精确的调用栈假设，内联会破坏它们。
- **历史上对 `defer`、`recover`、闭包的限制**。需要注意的是，这些规则随版本在演进。例如，`recover` 的限制因其与栈展开的兼容性改善而有所放宽；闭包内联的限制也在后续版本中被弱化。因此，对于特定复杂结构，最准确的方式仍是查阅当前版本的编译器行为。

---

### ⚡ 例外与增强：闭包与 PGO

Go 的内联并非一味保守，它有一些明确的“优待”和增强机制：

- **只被调用一次的闭包**：如果编译器发现一个闭包**只被调用一次**，其内联预算会被大幅放宽（`inlineClosureCalledOnceCost`），因为内联它几乎不会增加最终的二进制体积。
- **PGO（Profile-Guided Optimization）** ：这是 Go 内联走向“按实际热点更激进”的关键。从 Go 1.20 起，如果提供了 CPU 性能分析文件（`default.pgo`），编译器会对**热点调用点**提高内联预算。例如，默认预算可能从 80 提升到 **320**（4倍）甚至更高。PGO 让内联决策从纯粹的静态启发式，转变为数据驱动的优化。

---

### 🔍 如何观察和调试内联行为

最直接的工具是编译器的诊断标志 `-gcflags="-m"`。它可以输出编译器对每个函数的决策日志，直接告诉你某个函数“can inline”还是“cannot inline”，以及原因（如成本过高、被标记为 `//go:noinline` 等）。

```bash
go build -gcflags="-m" .
```

此外，`-gcflags="-l"` 可以控制内联的“攻击性”：`-l` 会禁用内联，而实验性的 `-l=4` 则会尝试更激进地内联非叶子函数，但这可能导致编译变慢或二进制膨胀，不建议在生产中默认使用。



Mid-stack inlining
--------------------

Go语言中的Mid-stack inlining​（中栈内联）是编译器优化技术中的一种内联策略，旨在提高程序性能。它允许编译器在函数调用链的中间位置​（而不仅仅是叶子函数）进行内联，从而减少函数调用的开销，同时控制代码膨胀。

针对函数内调用了不可内联的函数导致不可内联的问题, Go语言引入了`Mid-stack inlining`技术. 只要一个函数f本身足够简单, 即使调用了不可内联的函数g, f自己还是可以被内联.

无法对f进行内联的主要原因是Go的编译器对于此类内联操作无法准确的追踪堆栈和调用信息, 导致报错时无法准确输出信息. 对编译器进行改造以后即可修复此问题. 引入此优化后, Go语言有大约9%的性能提升和大约15%的体积增加

--------------

标准库的`sync`包中的`Lock`方法采用了`Mid-stack inlining`特性, 代码如下:

```go
func (m *Mutex) Lock() {
	// Fast path: grab unlocked mutex.
	if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
		if race.Enabled {
			race.Acquire(unsafe.Pointer(m))
		}
		return
	}
	// Slow path (outlined so that the fast path can be inlined)
	m.lockSlow()
}
```

上述代码对于加锁操作分为两个部分, 首先尝试CAS加锁, 如果失败则执行后续逻辑. 此处CAS操作的代价是确定的, 而`lockSlow()`逻辑非常复杂, 不可被内联. 

按照上述写法, 可以确保Lock方法本身可以被内联, 从而使得锁压力较小时性能较高.
